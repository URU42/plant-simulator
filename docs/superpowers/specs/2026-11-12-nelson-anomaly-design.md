# Nelson 8종 이상 생성·판정 설계 — 주입·멈춤 API와 상시 판정

작성일 2026-11-12. 팀의 Nelson 판정 계약(위키 `concepts/synthetic-nelson-anomaly-data.md`, `data-v3/DATA_CHANGE_SUMMARY.md`)을
시뮬레이터와 수집 서버에 옮긴다. 생성 방식의 근거는 `data-v3/support/nelson-20261112/`(`build_dataset.py`, `signal_engine.cpp`)다.

## 1. 의도

- 알람 요약 모델 테스트용이다. 모델은 `GET /{공장}/alarms` 응답을 통째로 받아 설비별 오류 내용을 구조화해 나눈다.
  테스트하는 쪽은 5분마다 `/alarms` 를 가져가고, 모델 답변을 별도 정답지와 대조해 채점한다.
- 지금은 값이 거의 정상이라 이상이 생길 때까지 기다릴 수 없다. 원할 때 특정 설비에 이상을 넣고(주입), 원할 때 정상으로 되돌린다(멈춤).
- 평소에도 이상이 저절로 생겨 설비마다 이상 시간이 약 10% 가 되게 한다. 그중 일부는 멈춤을 부를 때까지 남는 "고장"이다.
- 알람 판정은 Nelson 8종만 쓴다. 기존 경고·알람·정지 한계값 판정은 없앤다.
- 이 서비스는 센서 값 생성기다. 심각도·정비·고장 이력 같은 해석은 다른 서버(알람 요약 LLM 등)가 한다. 여기서는 값과 판정 사실만 낸다.

## 2. 목표 / 비목표 / 안티 목표

목표
- 정상 신호를 data-v3 방식(고정 μ·σ, AR(1), 규칙 위반 억제 표집)으로 바꾼다. 다섯 공장 274 태그 전부.
- 원시 표본(1초, 온도 10초)에 Nelson 8종을 상시 판정해 `/alarms` 에 낸다.
- 자동 이상(설비당 약 10%, 저절로 회복) + 지속 고장(멈춤까지 유지) + 주입 이상(API).
- 주입·멈춤 API, 정답지 조회 API.
- 메시지·DB 의 `quality` 를 `status`(설비 상태: `Good` / `Bad`)로 바꾼다.

비목표
- 실측 근사 물리 모델, 현장 오탐률 재현. 정상 구간은 일부러 깨끗하다(data-v3 와 같은 한계).
- 분리 실행(`--profile split`)에서의 주입·멈춤·지속 고장·정답지. 분리 실행은 자동 이상(저절로 회복)만 내고,
  `/anomalies` 는 비어 있으며, 재시작 이음매의 규칙 위반을 허용한다(생성기가 `ts_raw` 를 읽을 수 없으므로). (내 판단)
- 품질(측정 신뢰도) 개념, 결측·gap, 정비 정지, 기존 시나리오 이벤트, 우연한 잡음 알람.
- PostgreSQL 내보내기 구현(`table-plan.md` §6 문서만 고친다).

안티 목표
- 정답(원인·분류·조치)이 `/alarms` 에 실려 모델이 베끼기만 하면 된다.
- 정상 운전 중 잡음 위반이 쏟아져 넣은 이상이 묻힌다.
- 멈춤을 불렀는데 값이 정상으로 돌아오지 않거나, 다른 설비까지 바뀐다.
- 백필 하루치 생성이 통합 실행의 자원(CPU 500m · Memory 1Gi) 안에서 끝나지 않는다.

## 4. 결정 사항

### 4.1 판정 계약 (`common/nelson.py`, 하나의 구현)

data-v3 계약을 그대로 옮긴다. 시뮬레이터(억제 표집·상태 결정)와 수집 서버(`/alarms`)가 같은 모듈을 쓴다.

| 규칙 | 조건 (z = (값 − μ) / σ) |
| --- | --- |
| 1 | \|z\| > 3 |
| 2 | 9점 연속 z > 0 또는 9점 연속 z < 0 |
| 3 | 6점 연속 엄격한 증가 또는 감소 (차분 5개가 모두 같은 부호) |
| 4 | 14점 연속 증감 교대 (차분 부호가 12번 연속 바뀜) |
| 5 | 3점 중 2점 이상이 같은 쪽 \|z\| > 2 |
| 6 | 5점 중 4점 이상이 같은 쪽 \|z\| > 1 |
| 7 | 15점 연속 \|z\| < 1 |
| 8 | 8점 모두 \|z\| > 1 이고 중심 양쪽에 모두 있음 |

- 경계와 같은 값은 '밖'이 아니다. 같은 값은 추세·교대를 끊는다. 조건이 성립한 마지막 표본에 표시하고 과거로 소급하지 않는다.
- 판정은 **보낸 값**(구성안 `decimals` 로 반올림한 값)으로 한다. 생성기와 수집 서버가 같은 결과를 내야 한다.
- 결측·품질 불량이 없으므로 "Bad 창 제외" 규칙은 없다. `status` 는 판정 결과이지 판정 입력이 아니다.
- 규칙 7 과 정상 억제 표집: 15점 연속 \|z\|<1 은 정상 잡음에서도 자주 생긴다. data-v3 는 이것까지 억제했다(같은 방식).

### 4.2 구성안

- 태그에 `control: { mean, sigma }` 를 넣는다. 값은 `baselines.json` 그대로(274 태그 키가 구성안과 전부 일치함을 확인했다).
- `normal` 블록(base, noise_sd, daily_amp, drift_sd)은 지운다.
- RFCC 의 `limits` 는 `warn_lo = μ − 3σ`, `warn_hi = μ + 3σ` 로 다시 쓰고 `limit_basis` 를 "Nelson 관리한계 μ±3σ (baselines.json)" 로 바꾼다.
  다른 공장의 `limits` 는 자료 원문 참고값으로 마스터에 남기되 알람에는 쓰지 않는다. (내 판단)
- `delay_samples` 는 지운다. `config_version` 을 올린다.
- `decimals` 가 σ 에 비해 거친 태그는 반올림 단위가 0.1σ 이하가 되도록 자릿수를 올린다.
  지금 274 태그 중 38개가 0.3σ 를 넘고 8개는 σ 보다 크다(예: `TI-LO-C3101`·`TI-LO-C4101` 0.1 대 σ≈0.055).
  그대로 두면 규칙 2 모양(0.65σ)이 μ 로 반올림되어 정답지의 반응 태그에 규칙이 안 나타난다. (내 판단)
- HDS 는 `baselines.json` 에 없어 돌릴 수 없으므로 `plant_hds.yaml`·`runtime.yaml`·`scenario_dev.yaml` 과 HDS 신호 모델을 지운다. (내 판단)

### 4.3 정상 신호 (`simulator/` 새 신호 모델, 기존 `signal_model.py`·`rfcc_model.py` 대체)

- 태그마다 z 를 순차로 만든다: `z = ρ·clip(z_prev, −2, 2) + √(1−ρ²)·N(0,1)`, ρ = 0.12(온도 0.25).
  뽑은 z 로 규칙 위반이 생기면 최대 100번 다시 뽑고, 그래도 안 되면 마지막 표본을 그대로 쓴다(우연한 위반, 그대로 둔다).
- 값 = `round(μ + σ·z, decimals)`. 판정은 반올림한 값으로 한다(4.1).
- `speed` 태그는 이상 사건에서 바뀌지 않는다. RFCC 의 `driven_by` 짝(B-1201↔E-1202, C-1401↔T-1401)은 같은 난수열·기준으로 같은 값을 낸다.
- 하루 주기·느린 드리프트·공정 부하·연관 규칙은 없어진다.
- 순차 생성이라 상태(태그별 최근 14개 z)가 있다. 백필 → 실시간은 같은 생성기 상태로 이어 간다.
  재시작 때는 수집 서버의 마지막 측정 시각부터 이어 가며, 태그별 최근 14개 값을 `ts_raw` 에서 읽어 z 로 바꿔 상태를 복원한다. (내 판단)
- 시드: (runtime.seed, 태그 seed_key, KST 날짜). 같은 시드로 다시 백필하면 같은 값이 나온다.
- **속도 제약**: 다섯 공장 하루 백필(1초 태그 약 2천만 표본)을 통합 실행 자원 안에서 지금(Mac 약 7분)과 비슷하게 끝내야 한다.
  표본마다 파이썬으로 8규칙을 다시 세면 느리므로, 규칙별 누적 상태를 O(1) 로 갱신하는 판정기나 NumPy 블록 처리 등을 쓴다(방법은 작업자).

### 4.4 이상 사건 (모양·연관 태그·정답)

사건 = (설비, 규칙 번호, 시작, 끝). 끝은 자동 이상이면 정해진 길이, 지속 고장·주입이면 멈춤 요청 시각이다.

- **모양**: `signal_engine.cpp` 의 규칙별 z 템플릿(k = 반응 시작 후 표본 번호, u = U(−1,1)).
  1: 3.5+0.12u / 2: 0.65+0.18u / 4: ±(0.7+0.12u) 교대 / 5: k%3==2 이면 −0.25 아니면 2.35+0.15u /
  6: k%5==4 이면 −0.3 아니면 1.55+0.17u / 7: 0.025 고착 / 8: (k%4<2 ? +1 : −1)·(1.55+0.18u).
  3(추세)만 길이가 필요하므로, 끝을 모르는 사건에서는 −2.4→+2.4 를 60 표본 주기로 반복하는 톱니로 만든다. (내 판단)
- **연관 태그·방향·지연·회복**: `build_dataset.py` 의 `response()` 표 그대로.
  대표 태그 = 설비의 첫 vibration/shaft_vibration 태그(지연 0, 회복 5초, 규칙 7 은 회복 0).
  규칙 1·2·3·5·6 은 진동·베어링 온도·전류·윤활유 압력/온도가 반응(윤활유 압력은 반대 방향, 온도는 지연 40초·회복 60초이며 규칙 3 이 아니면 규칙 2 모양).
  규칙 4·8 은 흡입/토출 압력·유량·전류·차압·진동이 반응(유량·흡입 압력은 반대 방향, 지연 2초·회복 15초).
  규칙 7 은 대표 태그만. speed 는 반응하지 않는다.
- **회복**: 끝 시각부터 태그마다 회복 시간 동안 z 를 선형으로 0 쪽으로 줄이고(+0.08u), 그 뒤 정상 표집으로 돌아간다.
  직전 창 때문에 회복 직후 잠깐 남는 위반은 그대로 둔다.
- **분류·원인·조치**(정답지에만): `build_dataset.py` 와 같다. 7 = 계측 이상, 8 = 계측·제어 이상, 4 = 기계·제어 이상, 그 밖 = 기계 이상.
  자동 이상의 규칙 2 사건 일부(5건 중 1건, 사건 ID 에서 결정)는 "정상 운전 변화"다. 주입 사건은 늘 위 기본 분류. (내 판단)

### 4.5 자동 이상과 지속 고장

- **자동 이상**(저절로 회복): 설비·KST 날짜마다 일정표를 시드(runtime.seed, equip_id, 날짜)로 정한다.
  data-v3 `schedule()` 을 하루(86400초)로 줄인 것: 사건 길이 lognormal(ln 650, 0.52)을 200~1800초로 자르고, 사건 시간 합이 하루의 10.5% 가 되게 맞춘다.
  간격은 Dirichlet(3)로 나눈다. 규칙은 하루 안에서 1~8 을 고르게 돌린다. 백필 구간에도 생긴다.
- 그 설비에 지속 고장이나 주입 사건이 살아 있으면 겹치는 자동 이상은 건너뛴다(나중에 채우지 않는다).
- **10% 의 정의**: data-v3 와 같다. 태그별 위반 표본을 다음 표본 직전까지 유지해 시간으로 바꾸고 설비 안에서 합집합을 낸 비율.
  지속 고장·주입 사건이 차지한 시간은 이 비율에서 뺀다.
- **지속 고장**: 공장마다 실시간 시작부터 `persistent_fault_interval_min`(기본 15분)마다 하나씩 연다. 백필에는 없다.
  설비는 그 순간 지속 고장·주입 사건이 없는 설비 중 무작위, 규칙은 1~8 중 무작위다. 그런 설비가 하나도 없으면 그 회차는 건너뛴다.
  간격은 runtime yaml 의 `persistent_fault_interval_min` 으로 정하고, 환경 변수 `PERSISTENT_FAULT_INTERVAL_MIN` 이 있으면 모든 공장에 덮어쓴다(0 이면 끔).

### 4.6 주입·멈춤·정답지 API (수집 서버, 통합 실행 전용)

| 요청 | 동작 |
| --- | --- |
| `POST /{공장}/anomalies` `{equip_id, rule}` | 시뮬레이터 시각 기준 3초 뒤 첫 표본부터 사건 시작. 201 + `{event_id, equip_id, rule, start_at}` |
| `POST /{공장}/anomalies/{equip_id}/stop` | 그 설비의 살아 있는 사건(주입·지속 고장·자동 이상)을 지금 끝내고 회복을 시작. 사건이 없으면 404 |
| `POST /{공장}/anomalies/stop` | 그 공장의 살아 있는 사건(주입·지속 고장·자동 이상)을 모두 지금 끝내고 회복을 시작. 200 + 끝낸 `event_id` 목록(없으면 빈 목록). 앞으로 예정된 자동 이상·지속 고장 일정은 그대로 이어진다 |
| `GET /{공장}/anomalies?equip_id=&from=&to=` | 정답지. 사건마다 event_id, origin(`injected`/`spontaneous`/`persistent`), equip_id, rule, kind, cause, action, response_tags, start_at, stop_requested_at, end_at(마지막 태그 회복 끝) |

- 같은 설비에 자동 이상이 진행 중이면 주입이 그 사건을 끝내고 대신한다. 지속 고장·주입 사건이 살아 있으면 409(먼저 멈춤). (내 판단)
- 쓰기(`POST`)는 `/ingest` 와 같은 토큰 규칙: `INGEST_TOKEN` 이 있으면 `X-Ingest-Token` 필수, 통합 실행인데 토큰이 없으면 403. 정답지 `GET` 은 열어 둔다.
- 분리 실행에서는 `POST` 가 409("embedded only")를 돌려준다.
- 사건은 수집 서버 DB 의 `anomaly_event` 에 저장한다(정답지 겸 상태). 재시작하면 열린 주입·지속 고장을 이어 간다. 생성기는 창마다 이 상태를 읽는다.
- 3초는 시뮬레이터 시각이다(accelerated 모드에서는 시뮬레이터 3초). accelerated 도 지속 고장에서는 실시간 구간으로 본다.
- 그 공장이 아직 백필 중이면 `POST` 는 503("backfilling")을 돌려준다. 백필 중 시계가 앞으로 달려서 3초 뒤가 과거 데이터 한가운데가 되기 때문이다.
  `/{공장}/health` 에 실시간 여부(`live`)를 낸다. (내 판단)

### 4.7 메시지·저장 (`status`)

- `Sample.quality` → `Sample.status: Literal["Good", "Bad"]`, `value` 필수. 메시지 `schema_version` 2.0. 수집 서버는 1.x 를 400 으로 거절한다.
- 시뮬레이터가 판정해 `status` 를 채운다(그 표본에 규칙이 하나라도 성립하면 `Bad`).
- DB: `ts_raw.status`, `tag_current.status`. DB 스키마 v3, 이전 파일은 열지 않고 알린다(기존 방식). 배포 때 PVC 의 DB 는 새로 만든다.
- `/current` 의 `status`: 오래 안 들어오면 `NoData`, 아니면 받은 `Good`/`Bad`. 기존 `quality` 키는 응답에서 뺀다.
- 집계(`ts_10m`, `ts_1h`)의 `status`: 구간에 `Bad` 표본이 하나라도 있으면 `Bad`, 없으면 `Good`, 표본이 없으면 `NoData`. 평균·최소·최대는 모든 표본으로.
- 디버깅 화면의 "품질" 열 → "상태".

### 4.8 상시 판정과 `/alarms`

- 수집 서버가 받을 때마다(10분 배치가 아니라) 태그별로 판정한다. 태그별 최근 14개 값은 메모리에 두고, 시작할 때 `ts_raw` 에서 채운다.
- 판정 결과가 받은 `status` 와 다르면 경고 로그를 남기고, `/alarms` 는 수집 서버 판정을 따른다.
- `alarm_detail` 을 `nelson_alarm` 으로 바꾼다: `alarm_id, equip_id, tag_id, rule, direction(hi/lo, 규칙 4·7·8 은 null), occurred_at, cleared_at, last_hit_at, hit_count, value_at_occurrence`.
  심각도는 두지 않는다(알람 요약 LLM 이 판단). (태그, 규칙)마다 연속 위반을 한 건으로 묶고, 15 표본 연속으로 그 규칙이 성립하지 않으면 그 15 표본 중 첫 표본 시각으로 닫는다. (내 판단)
- `GET /{공장}/alarms?equip_id=&rule=&from=&to=&open=` 은 이 테이블을 낸다. 원인·분류·조치·사건 ID 는 싣지 않는다.
  `from`/`to` 는 "구간과 겹치는 알람"이다(`occurred_at < to` 이고 `cleared_at` 이 없거나 `≥ from`). 그래서 5분 전에 열려 아직 열린 알람도 다음 조회에 나온다.
  테스트하는 쪽은 `from` = 지난 조회 시각으로 부른다. 기본 구간은 없다. 공장당 하루 수천 행 수준이라 `nelson_alarm` 은 지우지 않는다(기존 `alarm_detail` 과 같음). (내 판단)
- 10분 배치는 집계·보관만 한다(한계값 판정 삭제).

## 5. 검증

- 판정기: data-v3 `verify_dataset.py` 의 손작성 사례(경계·같은 값)와 data-v3 NumPy 판정기(`build_dataset.nelson`)에 같은 입력을 넣어 비트가 같다.
- 규칙별 템플릿: 각 규칙 사건이 대표 태그에서 그 규칙을 실제로 성립시킨다(1·5 는 몇 초, 4 는 14 표본 안).
- 정상: 사건이 없는 하루에서 설비별 위반 시간 비율 < 0.5%.
- 자동 이상: 하루 백필에서 설비별 합집합 비율 9~11%, 모든 설비에서 8규칙이 다 나온다.
- 주입: 요청 후 3초 뒤 표본부터 `Bad`, `/alarms` 에 그 규칙 행. 멈춤 후 회복 시간 + 15 표본 뒤로 그 설비의 새 위반이 없다. 다른 설비는 영향 없다.
- 전체 멈춤: 여러 설비에 사건을 열어 둔 뒤 부르면 모두 닫히고, 회복 뒤 그 공장의 새 위반은 다음 예정 사건 전까지 없다.
- 재시작: 열린 주입·지속 고장이 이어지고, 정상 신호가 이어진다(이음매에서 규칙 위반이 생기지 않는다).
- 성능: 다섯 공장 하루 백필 시간과 메모리를 기존과 비교해 적는다.
