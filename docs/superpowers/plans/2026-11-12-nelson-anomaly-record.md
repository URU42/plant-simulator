# Nelson 이상 생성·판정 — 작업 기록

설계 `docs/superpowers/specs/2026-11-12-nelson-anomaly-design.md`, 계획 `docs/superpowers/plans/2026-11-12-nelson-anomaly.md` 를
과제별 구현 → 과제별 검토 → 브랜치 전체 검토 순서로 진행했다(2026-11-12~13). 이 문서는 진행 중에 대신 정한 것과 남긴 것을 적는다.

## 결과

- 과제 10개 + 최종 검토 수정 1회. 테스트 160 → 197개, 모두 통과.
- 실제 통합 실행(Mac): 다섯 공장 하루 백필 후 실시간까지 약 7.3분, RSS 약 243 MB. 1시간 생성 1.35~2.38초/공장.
- 자동 이상 합집합 비율: 설비·일 26건에서 9.90~10.08%.
- 생성기 판정과 수집 서버 판정 불일치 0건(하루 백필 + 실시간 + 재시작).
- 규칙 3 사건 하나(12분)의 알람 행: 160 → 14.

## 대신 정한 것 (틀렸을 때 비용)

| 정한 것 | 이유 | 틀렸을 때 |
| --- | --- | --- |
| 자동 이상 사건 시간 10.5% → 9.4% (하루 8122초) | 10.5% 에서 실측 합집합 11.0~11.2% (온도 회복 꼬리·우연 위반 포함). 요구는 "약 10%" | 비율 1%p 차이, 상수 하나 |
| 규칙 3 톱니 주기 60 → 20 → 16 표본 | 60 은 반올림에 증가가 끊김, 20 은 규칙 5·8 알람이 20초마다 열고 닫힘 | 상수 하나 |
| 억제 표집이 100번 실패하면 N(0,1) 한 번 뽑은 값을 그대로 | data-v3 와 같음 | 드문 경로 |
| 시작 전에 멈춘 사건은 버린다(`resolve`), 정답지에서도 뺀다 | 주입 직후 멈춤이면 데이터에 없는 사건 | 길이 0 사건이 사라짐 |
| 생성기가 외부 사건을 1시간+60초 되돌아보며 묻는다 | 창 크기에 따라 결과가 달라지던 문제 | 창마다 조금 더 훑음 |
| 주입·멈춤 시각 = max(ceil(sim_now)+3초, 이미 만든 표본의 끝) | 따라잡는 중에도 이미 보낸 데이터와 정답지가 어긋나지 않게 | 주입이 몇 초 늦게 걸림 |
| `live` 는 실시간 루프가 벽시계를 따라잡은 뒤에 켠다 | 켜진 직후 주입하는 사용 흐름 | live 가 한 창 늦게 켜짐 |
| 지속 고장이 열릴 때 그 설비의 자동 이상을 끝낸다 | 정답지가 생성 데이터와 일치 | 없음 |
| 지속 고장 첫 회는 다섯 공장이 같은 시각(시뮬레이터 실시간 시작 + 15분) | 설계 "실시간 시작부터 간격마다" | 백필이 끝난 뒤 15분이 아니라 시작 후 15분 |
| 빈 설비가 없으면 그 회차를 건너뛴다 | 설계 §4.5 | 없음 |
| 멈춘 고장의 회복 꼬리보다 새 사건이 우선 | 새 사건 시작이 정답지와 일치 | 멈춘 고장의 `end_at` 이 최대 60초 길게 적힘 |
| 통합 실행 중 `sys.setswitchinterval(0.001)` | 순수 파이썬 생성기가 `/health` 를 0.9초까지 막음 | 프로세스 전체 GIL 전환 비용이 조금 늘어남 |
| 수집 서버 판정의 마지막 시각은 `tag_current.ts` | `MAX(ts_raw)` 와 같고 시작 때 전체 훑기를 피함 | 없음 |
| 멈춤 응답에 `stop_requested_at` 추가 | 실제로 쓴 시각을 알려 줌 | 응답 전체를 비교하는 클라이언트 수정 |
| 잘못된 `from`/`to` 는 400, 잘못된 `PERSISTENT_FAULT_INTERVAL_MIN` 은 시작 오류, 생성기가 죽으면 POST 503 | 사용자가 만나는 오류를 분명히 | 없음 |
| `equipment-tags.md` 는 이 브랜치에서 고치지 않음 | 사용자가 다른 체크아웃에서 그 파일을 고치는 중 | 판정·RFCC 한계값 설명이 당분간 옛 내용 |

## 남긴 것

- 해결: 지속 고장 개수 상한. 공장당 동시 최대 3개(`persistent_fault_max_open`, 환경 변수 `PERSISTENT_FAULT_MAX_OPEN`), 상한이면 그 회차는 건너뛴다.
- 해결: `equipment-tags.md` 를 Nelson 판정·태그별 μ/σ·RFCC μ±3σ 참고값으로 다시 만들었다(사용자의 머리말 수정 포함).
- 해결: 기획서 1~4·8~9장을 지금 설계에 맞춰 다시 썼다(안내 문구 삭제).
- k8s 자원(CPU 500m) 에서 백필 시간 재측정(README 의 "약 15분" 은 옛 생성기 기준).
- 테스트 보강 여지: 지속 고장 상한이 재시작 뒤에도 지켜지는지.
- 자동 이상이 고장이 열린 같은 창 안에서 막 시작한 경우 정답지에 잘린 끝이 반영되지 않음(드묾).
- 설계 §4.6 표의 멈춤 응답 설명에 `stop_requested_at` 이 빠짐.
- 테스트 보강 여지: 규칙 2·3·5·6 의 low 비트, `CLOSE_AFTER` 경계(14·15 표본), 한 태그에 두 규칙 동시, 지속 고장 재시작 규칙, 409 Busy API.
